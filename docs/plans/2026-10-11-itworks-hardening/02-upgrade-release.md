# Upgrade, recovery, and patch release implementation plan

Status: planning only. U01–U07 are all **PENDING**. No implementation, installation, update, release tag, or publication is authorized by this document alone.

Decision: prepare a backward-compatible patch, provisionally **1.0.1**, after its release gates pass. Do not ship the currently audited tree under the existing 1.0.0 identity. The tag `v1.0.0` resolves to `0b972ac8232825d82f16023f54d3ccbeda443813`; the audit target is `7df722830da8fe3a3872459e06308d2d53f4153b`. Both report plugin version 1.0.0, although the latter contains the fixes listed under Unreleased. The patch version is a proposed implementation choice, not a version already assigned or published.

## Assumptions and boundaries

- Verified: `.claude-plugin/plugin.json` is the current version authority; the marketplace has no duplicate version. Five existing commands and state versions 1–3 remain supported. The patch does not add a required runtime interpreter, change the Markdown state schema, or introduce stable finding IDs.
- Defaulted: preserve original state bytes before any repair, including quotes, whitespace, encoding, line endings, and final-newline presence. New diagnostics may reject genuinely malformed records that older lint incorrectly accepted. Missing historical fields remain compatible drift, not corruption.
- Deferred to implementation evidence: exact supported Claude CLI version range and installed-cache discovery. Official commands must be checked against the pinned CLI's help and recorded. No claim of Codex/Agy installed-plugin compatibility follows from this Claude smoke.
- Scale: this is a local plugin and a small deterministic test suite, not a migration service. Python standard library is acceptable for developer tests. No Python dependency is added to session startup or normal linting. A future optional runner belongs to F01–F10, outside this patch.

Alternatives considered: documentation-only release is cheap but leaves bypasses; a schema migration and new runtime parser creates larger recovery and compatibility obligations; a shell-compatible patch with regression fixtures repairs observed defects while preserving current installations. Pick the third. Revisit a schema change only when explicit evidence identities and acceptance linking are implemented as a separately versioned opt-in protocol.

All commands below describe implementation-time work. They have **not** been run as part of this planning task. Each test must first fail for its intended defect where applicable, then pass after the smallest correction. Historical observed failures are asserted as historical behavior, not promoted to acceptable new behavior.

2. Copy state to a unique recovery directory **outside the project, plugin source, and installed-plugin cache**. For user repairs use an explicit external recovery location; never silently choose a path inside the directory being replaced. Set restrictive permissions because state may contain sensitive notes. Confirm source and backup hashes and file counts before proceeding. Keep the recovery point for at least 30 days and until the user has verified two subsequent work sessions, whichever is longer. A disposable CI temporary directory is adequate only for synthetic tests, not user recovery retention.
3. Build a repaired candidate in a separate staging directory. Only fill documented additive fields when absent. Keep original severity tokens and accepted words byte-for-byte in the recovery copy, and preserve their text without downgrade in the candidate. If moving a malformed line into valid structure cannot preserve its meaning, retain it verbatim as unresolved evidence and leave recovery BLOCKED for review; do not fabricate severity evidence, acceptance wording, paths, or closure proof.
4. Validate staging; show the exact diff and unresolved records. Require the normal one-shot resume confirmation for an interpretive rewrite; additive supported drift does not create a new approval loop. Rehash source before replacement; a changed source means abort and recompute, not overwrite concurrent work.
5. Because several Markdown files cannot be replaced atomically as a group without additional machinery, pause other writers, retain originals, and define a deterministic sequence. A failure mid-replacement triggers restore from the independent copy and validation of restored hashes. Do not claim atomic multi-file updates. User explicitly accepting a risk must remain associated with that risk under the existing grammar; missing or ambiguous association stays BLOCKED.
6. Exercise failure injection after backup, after staging, before first write, between file replacements, after replacement before lint, and during restore. For every point state whether no files changed or recovery restores the original manifest. Restore into a new empty directory and verify it before replacing damaged files. If automatic restore fails, leave both original backup and failed candidate untouched, report their paths, and require manual restoration; do not loop or delete evidence.

**Specific tests:** copying synthetic quote/CRITICAL records preserves exact hashes; backup under project root is rejected; existing backup is never overwritten; simulated ENOSPC/permission failure prevents writes; concurrent file edit aborts; missing historical fields produces only additive changes; malformed acceptance remains unresolved; injected partial replacement restores original bytes; newline and CRLF records round-trip unchanged in original backup. The runbook must contain executable, marked shell blocks for snapshot, staging-copy, verify-before-write, and restore-to-empty-directory operations. Tests extract and execute those **same blocks**, with only explicit fixture path/environment substitution, through `bash` against temporary files. Python is the test driver and hash oracle, not a second implementation of recovery. Inject faults at subprocess/filesystem boundaries. If the runbook sequence cannot be exercised faithfully, introduce a small shell helper called by both the runbook and tests in a separately reviewed implementation subtask; do not count a test-only copy of the algorithm as product protection. Live semantic repair by a model remains a separate unproven behavior.

**Commands:** `python3 -m unittest discover -s tests/integration -p 'test_state_recovery.py' -v`.

**Completion:** documentation includes independent backup, abort points, restoration instructions, 30-day retention, preservation checks, and a tested failure path. It explicitly prevents downgrading severity or accepting stale proof to make an upgrade appear successful.

## Premortem and recovery decision

Release is **no-go until the required matrix passes**. These are the failure stories the plan must answer before implementation is declared ready:

1. **Repair destroys both source and backup.** Recovery copy is outside project and plugin directories; verify hashes before staging; reject backup destinations within the mutation tree (U03).
2. **Update only half-loads.** Artifact selection happens only after extraction/hash checks; host tests verify loaded bytes in a fresh session. Any old/new mixture aborts qualification (U04/U05).
3. **Everything looks green but a critical vanished.** Candidate diagnostics, preservation hashes, quote/severity regression fixtures, and no silent candidate omission are release gates (U01/U02/U07).
4. **Rollback succeeds technically but restores a broken validator.** Keep patch diagnoses externally; old binary success never closes them. Restore state by verified bytes, retain 30-day recovery window, and requalify with the corrected reader before relying on a clean gate (U02/U03/U05).
